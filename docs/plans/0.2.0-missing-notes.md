# 0.2.0: create notes from missing links

Implemented on the development branch; not part of published 0.1.7.

- Following a missing note link offers Create Note or Cancel. Cancel and
  Escape create nothing. Cancellation receives initial keyboard focus.
- Simple wiki links such as `[[Next note]]` default to a timestamp-ID note in
  the workspace root. Uncheck **Use a timestamp ID filename** to create
  `Next note.md` beside the source instead (or in the root for an unsaved source).
  When a source tab is outside the workspace, ID creation in the workspace
  root is still available. The unsafe original-filename choice is omitted;
  no file is created beside that outside source.
- ID creation changes only the clicked wiki destination in an isolated undo
  transaction. `[[Next note]]` becomes `[[ID|Next note]]`; existing aliases and
  heading fragments survive. The source remains unsaved and uses normal crash
  recovery. Other occurrences of the same link are not changed.
- Existing ID links keep their requested ID when creating a missing note;
  explicit wiki paths/extensions and Markdown links keep the requested path.
  These exact-filename creations start as empty files. ID-named notes created
  from simple title links use the existing New Note heading behavior.
- Creation requires an open workspace and an existing parent folder inside
  it. Missing folders are not created. Files outside that scope, unsupported
  extensions, unreadable paths, dangling symlinks and duplicate-ID errors
  cannot be treated as missing notes eligible for creation.
- Native code rechecks lookup, workspace and destination at confirmation,
  then uses exclusive creation. Existing files are never overwritten. The
  source buffer is checked before creation and before any link edit. If it
  changes during file creation, retain the new file and report its ID without
  replacing source text. A stale preview must be followed again.
- Open the created note in a tab. Saving the source, undoing its link edit,
  or closing the new note does not delete the created file. No automatic save
  of the source is introduced.

Automated coverage includes cancellation, explicit confirmation and retry,
filename choice, clicked-link selection among duplicates, encoded preview
destinations, code exclusions, alias/fragment preservation, undo, exact-path
creation, ID creation, collisions, missing folders, workspace changes,
duplicate IDs and symlink boundaries.

## Manual validation

Confirmed by the user on macOS (M4 Mac mini):

- New Note offers a title; leaving it blank creates an ID-only filename.
- Following the missing `Next note` link opens the creation dialog and creates
  the note successfully.
- The source link has the expected `[[ID|Next note]]` format and stays unsaved.
- Undo and redo change the source link without deleting the created note.
- Following the new ID link switches to its existing tab without duplicating it.
- Cancelling creation of `Beluga Whale` creates no note and leaves the source
  unchanged.
- The user subsequently created `[[Beluga Whale]]` with the requested title
  and a unique note ID, without a filename collision.
- The exact-filename `Another whale.md` test resolves a second link to that
  note instead of creating a duplicate.
- Closing linked-note tabs and following their links reopens them successfully.
- Closing and reopening the source note preserves working links to those notes.
- Unchecking timestamp-ID naming for `[[Orca]]` creates `Orca.md` without an
  ID prefix; the unchanged wiki link opens it successfully.
- All three entry points work: a normal click in Preview, Cmd+click in Live,
  and Cmd+Enter in Source.
- After force quit and a development-app restart, recovery retains the
  unsaved ID-link edit, and following that recovered link opens the created note.

The macOS manual checks listed above passed.

Confirmed by the user on Linux using a locally built version:

- Note creation works with timestamp-ID naming and with the exact filename.
- The user interrupted the app from its launching terminal with Ctrl+C
  (SIGINT). After relaunch, the unsaved ID link was restored and following it
  successfully opened the created note. This is not a force-kill test.

Confirmed by the user on Windows using the test-branch installer:

- Notes behave as expected during creation.
- After terminating Textgate through Task Manager and restarting, notes remain
  available through recovery.

Manual creation and recovery checks have now been reported on macOS, Linux
and Windows. Linux and Windows checks beyond those explicitly listed above
are not recorded as individually passed.

## Code review and automated verification

The review found and fixed a workspace authorization issue: rebuilding a native
workspace grant from its filename could authorize a retargeted symlink. Missing
note creation now retains the original grant and rejects changed workspace
targets; New Note also checks that the workspace path still belongs to its
original grant. A regression test reproduced the failure before the fix and
checks that neither the original folder nor the new target receives a file.

Confirmation now checks the expected workspace and destination in one creation
request, without a second independent preparation. Tests cover stale
destinations, files appearing after confirmation was prepared, and switching
workspaces; those cases perform no unconfirmed write or overwrite.

Verification passed on macOS: 158 JavaScript tests, 78 Rust tests (including
two CLI tests), production frontend build, Clippy with warnings denied,
formatting, manifest version consistency and `git diff --check`. Existing
nonfatal toolchain debug-stripping and frontend chunk-size warnings remain.
No outstanding blocking findings were identified in this review. Subsequent
Linux and Windows manual creation/recovery results are recorded above;
automated verification here refers to the macOS run.
