# 0.2.0: rename notes and update links

Requirements and acceptance criteria, not an implementation or a claim that
multi-file renames are globally atomic. This covers renaming a note within
its current folder. Folder renames, cross-folder moves and changing note IDs
are separate work; their existing path-following behavior is not extended here.

## User choices

Before any mutation, show the old/new note name and a preview of each proposed
link edit, including the affected file, replacement count and before/after
context. Distinguish editor-only changes from closed-file disk writes. Show
blocked/unreadable files and incomplete scans; do not claim a complete update
when some candidates could not be inspected.

- **Rename and Update Links:** perform the rename and the reviewed link edits.
  Disable this choice when the plan is incomplete or unsafe.
- **Rename Only:** rename the note and follow its path in open tabs, with no
  content changes in any note or editor buffer. Explain that name-based links
  may stop resolving. Stable ID links continue to work.
- **Cancel:** change nothing, including the filename.

Declining link updates means choosing Rename Only, not cancelling the rename.
There is no silent default that rewrites other files.

## Identity and matching

- A title-only rename preserves an ID-bearing note's existing ID prefix.
  Changing an ID through this operation is refused with an explanation.
- Leave ID-resolving wiki links unchanged, including `[[ID Old title]]`; the
  display text/alias is not implicitly renamed. Use the resolver's agreed ID
  rules, rather than guessing identity from matching text.
- Update only parsed link destinations that resolve to the renamed note.
  Preserve link labels/aliases, heading fragments and all unrelated text.
  Include inline and reference-style Markdown links and name/path-based wiki
  links; rewrite a reference definition once when it is shared.
- Code, front matter, prose and similarly named files are not link matches.
  If a destination is ambiguous, report it rather than choosing a target.
- Use the authorized workspace boundary and existing symlink/identity checks.
  Deduplicate aliases so one physical file is reviewed and patched only once.
  No new filesystem grant is created by scanning or updating links.

## Preview freshness and application

1. Build the plan from a complete, scope-checked link scan/index. For open
   notes use current editor text and format, including unsaved edits; for
   closed notes use disk bytes. Record the source versions, open/closed state,
   target identity, workspace and proposed destination.
2. Before starting, revalidate those inputs and destination availability.
   If relevant content, open/closed state, scope or index completeness changed,
   perform no mutations and require a fresh preview/confirmation. Selection
   movement alone does not require a new preview.
3. Preserve current drafts in recovery successfully before the rename. Record
   the operation's old/new path mapping and progress durably so interruption
   cannot make a partially applied operation invisible.
4. Rename first using the existing non-replacing rename operation. A failed
   rename must leave every link unchanged. Do not replace an existing note.
5. Apply only the confirmed edits, checking each source again before its step.
   New typing or an outside edit stops further application; never escalate to
   forced overwrite. A newly discovered file is not permission to rewrite it.
6. Patch each open buffer in one undoable editor transaction, mapping its
   current selections through the edits and preserving earlier undo history.
   Every changed open buffer, even a previously clean one, stays unsaved.
   Do not silently promote an editor-only change to a disk write if its tab
   closes, or write through a newly opened tab as though it were still closed.
7. Rewrite each confirmed closed file through the existing conflict-checked
   atomic replacement flow. Preserve UTF-8/BOM, mixed line endings and every
   byte outside the edited destinations. Refuse unsupported encodings and
   unsafe/non-regular files; do not normalize or reserialize whole documents.

The target note's unsaved buffer is retained when its path changes. Rename
does not save that buffer. Recovery must retain the new path mapping and any
accepted editor patches without replacing the user's existing draft text.

## Failure, stopping and recovery

- Preflight failure or Cancel changes nothing. Failure of the rename changes
  no link contents. Once the rename succeeds, later failures can leave a
  partial operation; do not describe that as a cancelled, untouched operation.
- Stop at the first conflict/write failure. A Stop request between steps leaves
  completed steps intact; an atomic file write already in progress finishes
  before stopping. Do not attempt automatic rollback over possible new edits.
- Report the rename outcome, buffers changed but unsaved, closed files written,
  and pending/failed files with their reasons. Keep the durable progress record
  until the outcome is acknowledged or resolved. No failure is success-shaped.
- On restart, surface an interrupted operation and reconcile the rename using
  verified identity, not path spelling alone. Preserve recoverable drafts; if
  identity cannot be established, keep text recoverable and report uncertainty.
  Never automatically replay pending writes or recreate the old filename.
- Retrying rebuilds and previews pending work from current state using the
  recorded mapping. Reconfirm it; do not replay stale byte offsets or repeat
  completed edits blindly.
- Undo in one tab undoes that tab's link patch. It does not undo the filesystem
  rename or rewrites in other files; do not present it as a global undo.

## Acceptance cases required before implementation is considered complete

- All three choices have the specified effects, including a dirty target tab.
- Title-only ID renames leave ID links byte-identical; actual path-based links
  update while labels, fragments and unrelated occurrences remain unchanged.
- Reference definitions update once; code/front matter and other targets stay
  untouched. Ambiguous targets, incomplete scans and unsupported encodings
  block bulk application with an explanation.
- Typing, outside edits, tab open/close, workspace changes and a destination
  collision after preview invalidate the plan without overwriting unseen work.
- A rename failure changes no links. A later injected write failure or Stop
  produces an accurate partial result and does not change pending files.
- Open-buffer changes remain unsaved, preserve selection/undo behavior and
  survive recovery. Closed-file writes preserve BOM and mixed-ending bytes.
- Crashes immediately before/after rename and between file updates recover
  drafts and expose incomplete work without automatic writes or old-path
  recreation. A retry requires fresh review and handles completed steps safely.
- Repeat the relevant cases on Windows, macOS and Linux. Record unavailable
  manual platform checks explicitly rather than treating them as passed.
